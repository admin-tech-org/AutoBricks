## 為什麼「量成資料」——不用眼睛仿、也不抄原始碼

同一顆按鈕，三種做法的差別：

| 做法 | 得到什麼 |
|---|---|
| 用眼睛看 | 「深紅色、大概 40 多 px、圓角」——主觀，沒法驗證 |
| 抄 CSS 原始碼 | 原始碼寫的不一定是實際生效的（層疊、media query、死碼） |
| **量成資料** | `background: rgb(165,15,22)`、`height: 47.33px`、`border-radius: 100px`、`padding: 10px 30px`⋯⋯幾百個屬性全記下來，存成 JSON |

量成資料的核心價值是**數字可以機器對帳**：複刻品推上 WP 渲染後，用同一套方法把渲染結果
也量一次——`渲染出來的值 − 當初量到的值 ＝ 差異清單`，差幾 px 就修幾 px，減到零（或門檻內）
才算完成。「像不像」從主觀感覺變成一道**可以逐項打勾的減法**，不再依賴憑感覺猜。
`getComputedStyle` 給的是層疊、媒體查詢、繼承全套用完的最終值，所以解析層疊不用讀 CSS 檔，
跨網域也沒有讀不到的問題。

dump 為什麼「幾百個屬性全記、不挑」：只挑幾十個「看起來重要的」等於在賭有沒有猜中——
漏掉的那個屬性，之後 diff 對不上時查無可查，只能回頭重量。量是批次一趟的便宜動作，全記不虧。

附帶陷阱（規則本體在鐵律 2）：量到的是「用值」不一定是「設計值」——`line-height` 量到
`24px`，作者其實寫 `1.5`；照抄 24px，大標的行高就壞。量完還要判斷數字背後的設計意圖，
不能無腦照抄。

## 四本帳為什麼是四本——「視覺」不是第五本帳

「帳」是四個要結清的**問題**（結構／動態／精確度／整體長相），結帳靠兩份**證據檔**對答案：
dump 與視覺清單。同一份證據檔可以服務多本帳（dump 服務①③、視覺清單服務①④）——
所以「視覺」不是第五本帳，是 ①④ 共用的證據；帳④ 真正獨佔的題目只有「合成後的整體長相」。
記法：**前段＝DOM 樹×視覺雙把關（帳①），後段＝diff×視覺雙把關（帳③④）。**
視覺清單之所以要在處置**動手前**建：DOM 走訪保證「樹上每個節點都有決定」，但保證不了
「畫面上看得到的都有節點承接」——漏建的元件要靠清單在開工前現形，不是等收帳才發現。

## 為什麼零內建分析程式

網站千變萬化，**預先寫死的分析程式永遠會遇到沒料到的情況**：挑 50 個屬性記，下一站就用到
第 51 個。而 plugin 在使用者端是唯讀的、更新會整包覆蓋——**工具寫死在包裡＝永遠改不了**。
所以 skill 只給方法和要點，分析工具全部在使用者專案現場寫、照當站的狀況改、用完即棄。

自我檢查句：**這份 skill 要在「plugin 一行都不能改」的前提下跑完任何網站；做不到就是
skill 壞了，不是缺一支工具**——永遠不要用「往 plugin 加一支程式」來補洞。

## 為什麼帳④ 像素比對用門檻、不用 0

**0 分不出「做錯了」和「環境不一樣」。** 真的錯（位移、少東西、顏色錯）差距都很大，
門檻照樣抓到；只差 1、2 階的幾乎都是瀏覽器內部細節（文字邊緣的處理方式、小數捨入），
人眼看不見也修不動——去追它，時間就燒在 Chrome 身上而不是網頁身上。
標準精度收帳的「可歸因殘差」同理：次像素與 AA 不值得再花輪次。

## 為什麼 host 要少做事、多驗事

host 自己也會漂移——context 越長，越容易忽略規則、憑印象做事。這正是把施工派給全新乾淨
context 工人的理由：規則對乾淨 context 是滿強度的。host 能寫進 brief 的一律派出去，
自己只留「非得看過全部才做得了」的（驗收、整合、跨區一致性、全局）。

## 為什麼要 Monitor 看門狗、門檻為什麼是 30 分鐘

**不只 fullPage——任何 browser 操作都可能 hang**（CDP 抽風、頁面 wedged、網路卡住，或某個
還沒遇過的操作）。看門狗的最大用意正是：它**不需要知道是哪個操作卡住、也不需要事先列出
所有會 hang 的動作**，只要偵測到「這個工人不再產出」就能兜住——連預料外的卡死都抓得到。
工人卡死時自己救不了自己（它在等那台塞死的瀏覽器），所以救援只能由 host 做。

門檻是實測調出來的：一開始設 10 分鐘，但正常量測階段本來就常安靜 20–30 分（只寫 scratch、
甚至什麼都不落檔），連環誤報；調到 30 分才止住。**要改門檻，先回想這段。**
另外，實測最嚴重的一次卡死發生在**單工人的 Phase 1**——所以看門狗不限併行，凡有派工就開。

## 為什麼整頁高圖（fullPage）全面退役

實測兩次：高頁上 fullPage／CDP `captureBeyondViewport` 會 hang 或跑數十分鐘（80 分、45 分
各一次），塞死整條 MCP 連線；而且高圖給模型看會被縮到細節全糊，沒有驗收價值——又貴又沒用，
所以流程全面改視口分張（基準一屏一串、接縫跨縫圖、區高於視口就分張；「單張長元素圖」
只是高圖問題的縮小版，一樣不拍）。

真有理由要截 fullPage（不建議）的善後：它還會**永久弄髒分頁**（捲軸被藏、內容區寬度改變）
——量測全做完才截、截完該分頁報廢換新；卡住由 Monitor 看門狗兜。

## 為什麼 RWD 併入各區工人、不另開工人

工人把桌機收帳時，它的 dump、build 模組、這區的坑全在手上——另開新工人＝整套重讀 skill、
重量原站、重做 Phase 0，實測那份固定開銷幾乎等於白燒。這不違反「單元要小」：RWD 是
**同一區、同一份 dump 的另外兩個寬度**，不是第二件事；把它拆給新工人才是把一件事付兩次錢。

## 為什麼 plan.json 寫入要走加鎖 helper、不准用 Write／Edit 工具

plan.json 是併行期唯一的多寫者共用檔（Phase 2 高峰＝5 工人＋host）。撞法有兩種：
**寫壞檔**——兩個寫者位元組插花 → 壞 JSON（實測撞過）；原子寫回（temp＋`os.replace`）可解。
**互相蓋掉（lost update）**——A、B 同時讀到版本 1、各改自己的區寫回，後寫的把先寫的整檔蓋掉：
內容互不重疊照樣丟資料，而且檔案格式完全正常、無聲無息，可能到收尾對總帳才發現。
早期規則「重讀最新→只改自己那區→原子寫回」只縮小視窗、沒有歸零；Write／Edit 工具層
更是完全沒有鎖。加鎖 helper 用鎖檔互斥把「讀-改-寫」整段變成臨界區，兩種撞法一次封死；
鎖齡逾時可奪，是為了工人暴斃不留死鎖。

## 為什麼每區明細拆成 ledgers/<band>.json、done 由 host 標

plan.json 原本收所有每區明細（逐節點處置、四本帳 ledger），區越多總帳越肥：每個工人讀都
付整份的錢、寫都要過鎖。對照 ai-website-cloner-template 的檔案拓撲（一個工作單元一個 spec
檔、永不共寫）後拆分：每區明細改住 `ledgers/<band>.json`——一區一檔、只有該區工人寫，
零衝突免鎖，Monitor 還多一個心跳檔可盯；plan.json 縮回「全局設定＋狀態索引」，常態只剩
host 一個寫者（加鎖 helper 保留當保險，原子換檔仍必要——讀者眾多，直寫會被讀到半份檔）。
順帶修正 done 的語意：原本工人自己標 done、host 事後驗收，「done」分不清是自評還是驗收
結論；拆分後工人只能在自己的 ledger 標 `submitted`（申請驗收），plan.json 的 done 由 host
驗收過了才標——與「口頭回報不算數，落檔工件才算」「驗收是 host 最重的職責」一致。

## 為什麼要對抗式獨立稽核

四本帳是**施工者自己填的**，host 驗收又只是抽驗——實測證明這兩層擋不住跑版與漏掉的動態：
施工者急著收帳會不自覺放水；host 的 context 全場最長，走到後段驗收必然鬆掉。
所以必須由一個**全新乾淨 context、沒建過任何一區**的工人重新找碴——自己查自己＝白查。
