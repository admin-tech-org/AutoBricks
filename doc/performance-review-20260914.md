**AutoBricks 效能診斷 — 2026-09-14**

目前的主要瓶頸是 AI 驅動的量測、決策、分區施工與多層驗收流程。JSON 驗證本身很快；WordPress 每輪約數秒，也有改善空間。要顯著縮短整頁時間，優先把可重複的工作做成可靠工具、減少重測與返工。

這次是程式與既有產物審查，加上本機 Docker 實測；沒有重跑完整的 Claude 複刻工作，也沒有重新驗收原站的視覺／互動。下面將歷史紀錄、本次量測、程式問題與推論分開標示。

**現有架構**

專案是 Claude Code plugin。`src/` 只有 JSON 驗證與 Bricks schema 擷取，主要轉換邏輯由 skill 指示 AI 在執行時撰寫。

```text
網址
  → 全站探索、下載資產、擷取樣式、切區、現寫 toolkit
  → 分區工人：重量原站 → 自寫 build → JSON → 驗證 → WP
              ↑                          ↓
              └──── diff／互動／截圖修正 ──┘
  → 各區平板與手機驗收
  → host 抽驗、全頁整合、接縫驗收
  → 獨立稽核、派修、重驗、交付
```

值得保留的部分：直接輸出 Bricks 元素、優先原生可編輯欄位、簡化 wrapper、批次讀取 computed style、真正渲染驗證、每個工人的獨立分身頁、避免高頁 fullPage 截圖。問題主要在執行成本與工具可靠性。

**本次 Docker 實測**

啟動既有 WordPress／MariaDB 容器。實際執行環境為 WordPress 6.8.3、Bricks 1.12.5、PHP 8.2.29；版本取自容器執行結果，不能只看 compose image tag。

使用上述 256 元素模板建立新的測試頁 **199**；後續兩次只更新這次新建的頁面。模板不含 global classes 與 code 元素，因此本次推送沒有測試全站 class 合併或自訂 JS 執行。

| 工作 | 本次結果 | 測法 |
|---|---:|---|
| 15 份歷史模板的 JSON 讀取＋驗證 | 各樣本中位數約 0.4–10.9 ms | 每份 5 次、同一 Python process；13–801 元素 |
| 256 元素模板的完整驗證 CLI | **0.151 秒**中位數 | `uv run python src/validate_template.py`，3 次 |

| PHP 推送 WordPress | **5.501 秒**中位數 | 5.890／5.501／5.343 秒；含 WP 啟動與 metadata 寫入 |

容器剛啟動後，第一次讀舊頁 157 曾 45 秒無回應而逾時；靜態檔約 0.053 秒。本次未定位該次逾時原因，不將它當作穩態速度，也不直接歸因於 Windows mount。

一輪「驗證＋複製＋推送＋取得 HTML」依本次中位數相加約 **10.4 秒**，尚未包含 AI 思考與瀏覽器操作。假設序列執行 100 輪，光這些工作就約 17 分鐘；100 輪只是示例，沒有逐輪紀錄能證明歷史案例實際跑了幾輪。

**具體瓶頸與返工來源，依優先順序**

1. **每個網站現寫一次通用基礎工具。**

   [replica skill](../skills/replica/SKILL.md:98) 明定「零內建分析程式」。同站已有 toolkit 共用機制，並非每區都從零寫；但換站仍需 AI 重新產生量測、diff、覆蓋檢查、build 和 push 骨架。現存腳本很多只是 selector／檔案路徑不同，適合參數化。

   建議保留一套有版本、可測試的預設 toolkit，另外允許每站 adapter 與 fallback。Plugin 唯讀不妨礙呼叫其中的固定程式，也不妨礙在使用者目錄載入站別擴充。「工具可處理未知網站」與「每次重寫底層工具」可以拆開。

2. **七態掃描外層批次，內部仍大量序列通訊，狀態語意也不精確。**

   [seven_state.js](../tmp/toolkit/seven_state.js:44) 先逐節點取得 attributes，再對每種狀態逐節點 force、讀取、逐節點 clear。N 個節點約有 `N + 7 × 2N + 4` 次顯式 CDP send，外加 page.evaluate 的通訊。以 N=730 示意，約 10,954 次；這是依程式推導的呼叫數，不是本次瀏覽器計時。

   所有節點同時被 force hover／focus，可能出現真實操作無法達成的組合；讀到 transition 起始格又需要另外補驗。例外路徑沒有 `finally`，也沒 detach session，失敗後有狀態殘留風險。

   建議由樣式規則、互動語意、事件與代表元件找候選；對候選逐個驗證「觸發目標及受影響的後代／相鄰節點」。普通靜態節點不必全部跑七態。候選不明時再擴大掃描；強制 pseudo 不可取代真正點擊、捲動或鍵盤驗證。清理必須在 `finally` 執行。單純把全部 CDP calls 改為無上限並行會有狀態互相污染問題。

3. **比對工具有可重現的假通過，後段只能靠人式稽核補洞。**

   [box_diff.py](../tmp/toolkit/box_diff.py:32) 的本次重現如下：

   | 輸入差異 | 舊工具結果 | 問題 |
   |---|---|---|
   | 原站有節點，render 是空物件 | 提示缺 label，但仍印「無差異」，exit 0 | 缺節點沒有納入失敗條件 |
   | 原站有 width，render 缺 width | 無差異 | 缺屬性被略過 |
   | opacity 1 → 0.6 | 無差異 | 把 0.5px 的容差套到無單位 opacity |
   | 兩邊陰影都有透明層，但可見陰影不同 | 無差異 | 發現任何透明層就忽略整個 shadow 值 |

   [重現輸出](../data/20260914-performance-audit/diff-reproductions.json)。這是舊批次的臨場 toolkit，不是 `src/validate_template.py`；不能混為同一個 gate。

   建議把缺節點／缺屬性獨立列為 fail、依屬性單位定容差，保留陰影中的可見層，回傳結構化報告與非零失敗碼。也應移除無條件把 `max-width:none` 視為 `100%` 的正規化：兩者在不同容器條件下可能有不同結果。比較新舊 DOM 必須使用穩定的來源→Bricks 對照，不能只拿各自走訪序號配對。

4. **前置量測、各區重測、host 抽驗、最終稽核與收尾有重複成本。**

   [Phase 2](../skills/replica/SKILL.md:526) 要求每項自己重量；各區三寬度結帳後，host 抽驗、獨立稽核、收尾又驗。最後稽核確實找出 6 個缺陷，包含捲動導覽高亮缺漏和平板標題換行，因此直接拿掉 QA 並不合理。

   建議一次保留完整原站快照、版本及量測條件，後續只補缺項／變動條件；讓機器完成全量覆蓋與幾何檢查，把人工式判斷集中在特殊互動和最終整合。修正後只重跑受影響區域及相關接縫，避免每層重新探索整頁。

   既有 dump 約 16.1 MB，但 skill 已明確禁止整包讀進模型。改善方向是保留完整原始證據、提供精簡摘要與差異查詢，不能把檔案大小直接當成輸入 token 數，也不必為了省 token 刪掉原始量測。

5. **並行沒有消除串行前置與共同狀態問題。**

   時間紀錄顯示 Phase 1 當次仍由單一工人完成，約 58 分鐘。接棒在 23:06:21 因 `No transcript found` 失敗，後續重新開工人。實際多付多少 token 未能精算，但固定載入開銷確實重來。

   主 skill 有 637 行、57,874 bytes，每個工人還被要求重讀全文與經驗檔。應按角色給必要規則、重用已驗證產物，並把排程與 checkpoint 放在程式中。不要只靠模型記得收帳、接棒與寫進度。

   舊 [push.sh](../tmp/push.sh:59) 仍讓工人直接 read-modify-write 共用 plan.json，與現行「host 單寫者」規則不一致；無鎖且非原子寫入，存在更新互蓋風險。這次未進行併發破壞測試，不能斷言某次資料遺失必由它造成。

   [push-template.php](../docker/push-template.php:54) 的全站 global classes 合併也是 read-modify-write；不同分身頁並不隔離同一個 WP option。建議全局設定／classes 由 host 統一提交，工人只產區域內容。這個批次 global classes 為空，所以不是該批次已證實的瓶頸。

6. **schema 擷取漏掉中間父類別，增加無效警告。**

   [extract_bricks_schema.py](../src/extract_bricks_schema.py:58) 逐檔 regex 抽 controls，驗證時只加 `__base__`。本機 Bricks 的 `Element_Div extends Element_Container`，因此 div 的 `tag`、`link` 合法繼承卻未列在 schema。

   最新模板驗證有 15 個 warning，其中 13 個是這類 tag／link 警告，另外 2 個是結構警告。應補繼承解析或在已安裝版本內擷取 runtime controls；保留必要的真警告，減少 AI 反覆查證合法設定的成本。

7. **WP 執行成本是次要但可累積的因素。**

   現有 compose 把整個 WordPress 綁在 Windows 主機目錄。本次 WP bootstrap 約 5 秒，值得另做 Windows bind mount 與 Linux filesystem／named volume 的 A/B；目前只有基準，尚未證明能快多少。遷移要保留 theme、uploads、資料庫與可回復路徑。

   PHP／JSON 的 docker cp 各不到 0.1 秒，先優化它們收益小。更有價值的是減少無意義的 push／reload 輪次、確認 PHP 載入與快取設定，並記錄 browser action 的實際等待時間。

**策略篇幅與認知負荷**

目前策略確實冗長，而且角色需要同時維持的規則太多。這會增加載入、推理與核對成本，並提高遺漏或誤解要求的風險；本次沒有同模型的精簡前後對照，不能把某個時間比例直接歸因於 prompt 長度。

工人的定義要求讀完整主 skill（637 行、約 58 KB）與本機經驗檔（346 行），再加自己的指令（70 行），光這三份就約 **1,053 行**；尚未包括 plan、brief、schema 與施工資料。這是檔案篇幅，不等同實際模型 token 計費量。

| 負荷來源 | 目前可見情況 | 建議 |
|---|---|---|
| 同時維持太多分類 | 四本帳、三軸量測、五層行為階梯、Phase 0–4、分身／單台、標準／pixel | 入口只留一條執行路徑；其他模式在觸發時載入 |
| 相同要求反覆敘述 | 四本帳在全貌、定義、工人指令、施工步驟、收帳與驗收出現多次 | 一份正式驗收契約；其他步驟引用它，避免多份副本各自演化 |
| 角色責任混讀 | 區域工人必讀 host 的排程、全局整合、稽核與收尾規則 | worker 只拿本區輸入、輸出、限制、驗收、退出條件 |
| 新舊寫法共存 | 併行段要求各區獨立模組；Phase 2 又指示在共用 build_template.py 新增函式並掛 main | 固定唯一的輸出介面，讓整合器發現模組，不由工人共同改主檔 |
| 行政動作靠 AI 記得 | 寫帳、維護進度、更新 PAGE_ID、加鎖、還原量測狀態 | 由 runner 自動處理，寫入事件與結構化結果 |
| 每個例外都變成主流程禁令 | 版本地雷、截圖事故、狀態污染等混入通用流程 | 能測的變測試，能由程式保證的變程式；其餘按功能查閱 |

特別需要注意「流程看起來完整」與「執行證據完整」的落差：工人交四本帳、host 標 done 後，最終稽核仍找到漏行為；舊 diff 也會假通過。增加更多「必須」「禁止」無法替代可執行的檢查。

建議拆成四個清楚的責任層：

- **總控入口**：確認來源與交付精度、呼叫 runner、處理無法自動解決的例外。短到能快速讀完即可；約 80–150 行可以作為編寫目標，不是模型效能定律。
- **區域工作契約**：輸入是本區快照、資產索引與目標 schema；輸出是 band JSON、來源對照與未解決項。工人不必管理瀏覽器隊、全站 plan 或發佈。
- **固定執行程式**：擷取、產 ID、合併、驗證、推送、比較、checkpoint、還原狀態。規則能用程式保證就放在這裡。
- **按需參考**：互動重建、RWD、版本地雷與事故理由；遇到對應問題再讀。

工人每天實際需要維持的流程可以收成五步：**讀本區資料 → 決定 Bricks 結構 → 產出 → 看機器差異並修正 → 提交或標未解決**。完整證據由工具持續落檔，驗收標準保留在單一來源。這樣既減少認知負荷，也讓下一次調整規則不必同步修改多個段落。

**建議的改造順序**

| 順序 | 具體工作 | 如何驗證收益 |
|---|---|---|
| 1 | 固定 diff、coverage、進度寫入；補缺節點、單位容差、繼承 schema | 上述錯誤案例確實 fail；合法 div 設定不再警告 |
| 2 | 把 capture／資產收集／Bricks emitter／push 做成參數化工具，保留站別 adapter | 同一網站第二次執行不重寫 toolkit；統計前置耗時與模型呼叫數 |
| 3 | 量測快照與穩定 node map；候選互動掃描；可重用元件 | 保持全量覆蓋，減少重量、CDP call 與 context 輸入 |
| 4 | 每階段、每區、每輪記耗時／缺陷變化／退出原因；操作分段與心跳 | 找到真正卡住的 browser action；不只等 30 分鐘沒產物才發現 |
| 5 | 依相依性重驗、一次整合稽核；先交可編輯預覽，再處理精修 | 分別追蹤「首版可用時間」與「完成 QA 時間」，品質指標不混用 |
| 6 | Docker filesystem／PHP 設定 A/B | 使用同模板、同資產、同併發比較中位數與尾端延遲 |

先做 1–3，通常比繼續加工人或全面換較快模型更直接。可節省多少仍需改造後用同一份快照與同一套驗收條件比較，現在沒有依據承諾縮到幾分鐘。

「標準精度」目前仍要求盒尺寸／位置 ≤0.5px，只是略過部分不可見殘差；它與「設計部可先改的草稿」是不同交付目標。若採預覽／完整兩階段，必須清楚標出尚未驗收項目，不能把降低要求包裝成同品質加速。現行已有「同問題兩次無改善就 manual」的規則，缺的是可執行的區域預算與退出狀態。

針對「標準模式仍約六小時」的下一個最小實驗，建議用同一份來源快照與同一份驗收清單，先替換重複工作：共用擷取／比較工具、穩定來源對照、常見 Bricks 元件產生器與按變更範圍重驗。先量清楚首版何時產生、多少時間花在修正，以及哪些缺陷導致重做；保持驗收要求不變，確認這些工程改善本身的收益。

另可將「整頁可編輯預覽」提早：先完成全頁結構、主要字型／色彩／圖片與 RWD 骨架，再集中驗證與修正互動、版型和接縫。預覽階段清楚列出未驗項目，不必等每區所有帳冊都結清才看到整頁。若之後仍需調整精度，應另行定義可接受差異並獨立比較，避免混淆工具加速與降低驗收要求的效果。現階段沒有依據承諾六小時能縮到某個固定分鐘數。

**如果來源其實多半是自家 Elementor 網站**

專案已有 [Elementor 直轉研究](../data/elementor-direct-convert-research.md)，此批次快照也帶 Elementor 標記。若能取得源站正式匯出資料與相依資產，值得優先做「結構資料轉換 → Bricks → 渲染驗收」的小型實驗；常見容器／標題／文字／圖片／按鈕先走固定 mapping，特殊 widget 再交給 AI。

這條路需要源站資料存取，不能假設任意公開 URL 都能取得。預設值、全局樣式、資產 ID、斷點與動態內容仍須處理；最終視覺／互動 QA 也要保留。本次未重新核實舊研究中的外部工具與 API 現況，不將其市場盤點視為最新結論。
